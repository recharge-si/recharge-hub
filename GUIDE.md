# Continuation guide for Claude

## Current task

The user asked for two related changes:

1. Make the Exceptions screen incremental (`Load more`) instead of rendering a
   large list at once.
2. Fix the Shopify ↔ MetaKocka stock-sync failure shown in the supplied
   screenshot, and prevent repeated/clumsy exception rows in the future.

This guide was written on 2026-08-26. No source-code changes for the task have
been made yet. The working tree was clean when this guide was created.

## Verified diagnosis

The local PostgreSQL data showed one `shopify_to_mk` source named `Partner
Supply` failing with:

`MetaKocka rejected the request: Internal server error.`

It had 24 consecutive failures. The other `mk_to_shopify` source was healthy.
The open exception table contained 13 separate `stock_sync_failed` rows for the
same source, one per five-minute failure (attempts 12 through 24). This is a
real bug, not just a visual issue:

- `src/jobs/handlers/sync-inventory.ts` raises a location-level exception after
  12 failures and includes `sourceId` in `detail`.
- `src/adapters/db/repositories/exception.server.ts` only deduplicates rows
  with an `orderId`. For orderless stock failures it always inserts a new row.

MetaKocka's official `warehouse_stock_sync` documentation (fetched from the
official `metakocka/metakocka_api_base` repository; do not make a live company
call) says that `sync_stock` requires the total stock for all warehouses in one
request. The current reverse-sync path calls `syncStockToMetakocka` separately
for one source/warehouse and omits the other warehouse. That violates the
destructive endpoint contract and is the primary integration defect to fix.
The same official document exposes `include_current_stock`; use it only as
documented and keep the final behavior covered by recorded fixtures/tests.

Additional observed facts:

- `Partner Supply` uses MetaKocka warehouse id `678900000069` and the main
  warehouse is `678900000004`.
- Shopify currently has 39 mapped inventory levels for the failing location;
  two are negative (the code already clamps managed writes to zero).
- The MetaKocka API user email is configured and trimmed; credentials are not
  the apparent cause.
- The worker logs show the warehouse read succeeds and only the reverse
  `sync_stock` write fails.
- No live MetaKocka probe was performed. Project instructions explicitly forbid
  one without human approval and the designated test company.

## Intended implementation

### 1. Exceptions repository and migration

Add a nullable `dedupeKey` column to `Exception` and an additive migration with
a partial unique index for open rows, scoped by `(shop_id, kind, dedupe_key)`.
Use keys such as `order:<orderId>` for order exceptions and
`source:<sourceId>` for stock conditions. `raiseException` should update an
existing open row by this key and handle a concurrent unique violation safely.

The migration should consolidate existing duplicate open stock rows for the
same source before creating the unique index (keep the oldest row, copy the
newest message/detail into it, remove the invalid duplicate rows). Do not edit
an existing migration. The cleanup target is only duplicate open exception
conditions generated by this bug.

Files:

- `prisma/schema.prisma`
- new `prisma/migrations/<timestamp>_exception_dedupe/migration.sql`
- `src/adapters/db/repositories/exception.server.ts`

Keep tenant filtering on every query. Add a pure helper/test for the dedupe-key
decision if useful.

### 2. Exceptions screen pagination

In `src/web/routes/app.exceptions.tsx`, read a bounded `limit` query parameter,
load a small initial page (five rows is appropriate for the wide table), and
render an `s-button`/link labelled `Load more` that increases the limit. Do not
load all open rows in the loader.

The loader needs a count/group-count query so group headings and bulk action
labels remain truthful when only part of a group is loaded. The bulk action
path may intentionally load all rows for the requested operation. Fix the
existing `resolve-kind` filter: it currently requires `row.order`, which means
orderless stock exceptions cannot be bulk-resolved.

Likely files:

- `src/web/routes/app.exceptions.tsx`
- `src/adapters/db/repositories/exception.server.ts`
- optionally `src/web/lib/exceptions.ts` for a pure limit parser

Preserve the existing Polaris web-component style and 375px responsive table.

### 3. Shopify → MetaKocka write hardening

Refactor `handleSyncInventory` so reverse-sync sources are processed as one
company-wide snapshot:

1. Read current stock for every cached MetaKocka warehouse, not only the
   reverse-mapped source.
2. Read Shopify on-hand for each reverse source.
3. For the mapped warehouse, replace managed SKU quantities with Shopify's
   clamped on-hand; preserve every unmanaged MetaKocka line exactly.
4. For every other warehouse, preserve the current MetaKocka lines exactly.
5. Skip the write when all managed values already match.
6. Send one `sync_stock` request containing the combined snapshot. Abort the
   destructive write if any required warehouse read fails.
7. Record success/failure for each reverse source without allowing one source
   to abort the whole inventory sweep.

Useful adapter changes:

- Add a pure `buildCompleteCompanyStockList` helper in
  `src/adapters/metakocka/sync-stock.ts` and test that it preserves lines from
  non-managed warehouses.
- The official stock response can contain multiple rows for the same
  product/warehouse (microlocations). `src/adapters/metakocka/stock.ts` should
  aggregate those rows by warehouse and product before callers put them in a
  `Map`; otherwise the last microlocation silently wins.
- With multiple warehouses, echo validation in `sync-stock.ts` must key by
  `(warehouse_id, product_code)`, not product code alone.
- Include the documented `include_current_stock` request field if the chosen
  behavior is supported by the recorded contract; add a fixture assertion.
- Missing `apiUserEmail` must be recorded as a failed sync (not silently
  returned as success), because no write happened.

Relevant files:

- `src/jobs/handlers/sync-inventory.ts`
- `src/adapters/metakocka/sync-stock.ts`
- `src/adapters/metakocka/stock.ts`
- `tests/unit/sync-stock.test.ts`

Do not call MetaKocka while developing or testing. Use mocked fetches and
recorded fixtures only. Be explicit in docs if a behavior is based on official
documentation but still awaits designated test-company verification.
